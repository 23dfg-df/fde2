# 第一课：看懂一次文档解析

这节课只做一个练习：**读懂并复跑“中文资源使用通知”**。目标是能把输入、模型输出和评测结果连起来解释。完成一次请求是实现证据；能够独立解释和复跑，才开始构成你的学习证据。

## 先做练习：读懂并复跑中文通知

先按项目 README 打开平台并确认模型就绪。本课不重复安装、启动和连接命令。

动手前，先写下三个预测，不必答对：

1. 图片中的哪些内容必须被识别出来？标题和“合成教学样本”这一行算不算？
2. 如果接口成功返回，但少识别了一行，任务状态和评测分数分别能说明什么？
3. 同一张图复跑两次，耗时和显存读数一定相同吗？

按以下顺序做，先不要打开参考答案全文：

1. 选择内置的“中文资源使用通知”，页面 ID 为 `sample-01`。只选这一页。
2. 选择**纯文本识别（适合 CER）**，对应任务值 `structured_parse`。保留默认 `max_tokens=2048`。
3. 提交一次解析。等待页面结果完成，查看原图和原始输出，逐行找出遗漏、多余文字、错字或顺序问题。
4. 保存本次任务的 JSON 记录或结果截图，记下任务 ID、任务类型和结束原因。
5. 等待本次任务结束后，以同一页、同一任务类型和同一参数复跑一次。记录第二个任务 ID，再比较结果与指标。

提示：先对照原图，再看分数；不要为了让分数好看而改参考答案。若模型未就绪、任务失败或输出截断，也保存错误和参数，它们同样是排查证据。本轮不用换模型、不加并发、不批量处理六页。

## 从页面到结果，中间发生了什么

可以先把平台理解成六个连续环节：

```text
选择样本或上传文件
        ↓
准备每一页的图片
        ↓
应用通过 HTTP 请求 vLLM
        ↓
HunyuanOCR 根据图片和指令生成文字
        ↓
规则评测，并保留原始输出
        ↓
写入 SQLite 任务记录，页面展示结果
```

**第一步：接收输入。** 内置样本已经是 PNG，服务读取图片及样本清单中的参考信息。上传入口则接收 PNG、JPEG、WebP 或 PDF，单个文件上限为 12 MiB。上传成功只表示文件已被接收并处理，不表示模型已经识别了它。

**第二步：把每页变成模型能看的图片。** 普通图片会校正 EXIF 方向、转换为 RGB，并将长边限制在 1600 像素以内。PDF 使用 PyMuPDF 将每页渲染成 RGB 图片，一次接受 1～6 页；这叫“栅格化”。这里走的是看页面图像的路线，并没有直接把 PDF 内嵌文本当作识别结果。缩小图像会减少处理量，也可能让小字更难辨认。

本轮选的 `sample-01` 已经是 1200×1600 的 PNG，因此不经过 PDF 栅格化。理解完整流程，不等于本轮必须逐个尝试所有入口。

**第三步：应用组织模型请求。** 应用把图片编码成 Base64 数据地址，与一段任务指令放在同一条消息中，再请求 vLLM 的 `/v1/chat/completions` 接口。消息同时带图片和文字，所以称为多模态请求。Base64 只是图片的传输表示，不是模型提取出的文字。

**第四步：模型执行推理。** vLLM 是运行模型并提供 HTTP 接口的服务；HunyuanOCR 是实际使用的模型。模型根据图像和指令逐步生成输出 token，服务把生成文字和用量等信息返回应用。`max_tokens` 限制最多生成多少 token，不保证一定生成这么多，也不是图片尺寸或汉字数量。

**第五步：应用评测输出。** 有参考答案的内置样本可以按对应规则评测。上传文件默认没有参考答案，因此可以获得识别结果，但不能凭空产生可信的准确率。程序不会因为返回了文字，就自动宣布内容正确。

**第六步：保存与展示。** SQLite 保存页面信息和任务记录，图片文件另存在磁盘上。任务记录包含任务类型、模型及版本信息、参数、各页状态、原始输出、耗时、显存快照和评测结果。它让你能复查“哪次请求产生了哪份输出”，并不负责模型计算。任务创建和执行状态也会逐步写入数据库，并非只在最后保存一次。

代码对应位置：[图片处理](../backend/images.py)、[模型请求与任务编排](../backend/service.py)、[规则评测](../backend/evaluation.py)、[SQLite 记录](../backend/repository.py)。第一次阅读只需找到对应函数，不要求现在理解每行实现。

## 为什么本课必须选对任务类型

三种任务使用同一个模型，但给模型的指令不同，评测口径也不同：

| 任务值 | 要求模型做什么 | 读结果时注意什么 |
| --- | --- | --- |
| `structured_parse` | 提取图片中的文字 | 用于本课的全文 CER 评测；名称中有 structured，也不代表输出必然是 JSON。 |
| `doc_parse` | 按阅读顺序输出正文，使用 Markdown，表格使用 HTML，公式使用 LaTeX，并忽略页眉页脚 | 内置文本参考包含全部可见文字，和该任务的忽略规则不一致，因此不计算全文 CER。 |
| `table` | 将表格解析为 HTML | 表格样本检查 HTML 单元格文本覆盖，不用整段 HTML 与正文算 CER。 |

中文通知的参考文本包含标题、合成样本标记、编号、日期和正文。不能一边要求模型忽略某些内容，一边把这些内容的缺失全部算作模型错误。**先确定任务要求，再确定参考答案和指标。**

## 这是推理实验，还是训练实验

本课是**推理**：加载已有权重，给模型图片和指令，得到输出。当前请求不计算训练损失，不反向传播，也不更新模型权重。

**训练或微调**还需要训练数据、目标输出、损失计算、优化器更新和训练后验证。页面上的参考答案只交给评测规则用于比较，没有随本次请求拿去训练模型。重复运行十次，或者保存十条 SQLite 记录，也不等于模型学习了十次。

GPU 被使用只能说明它参与了计算。训练和推理都可能使用 GPU，不能仅凭显存占用判断正在训练。

## 这几个数字应该怎样读

| 指标 | 本平台实际测量的内容 | 不能直接得出的结论 |
| --- | --- | --- |
| `elapsed_seconds` | 应用从发起模型 HTTP 请求到解析返回内容的墙钟时间，包含服务端排队、处理、生成及通信等开销 | 不是纯 GPU 算子耗时，也不等于点击按钮到页面显示的全部耗时。 |
| `input_tokens` / `output_tokens` | 模型服务返回的实际 token 用量；缺失时不编造数值 | 不是逐字统计，也不应把输入 token 简单解释为提示词汉字数。 |
| `average_output_tokens_per_second` | 输出 token 数除以上述 HTTP 耗时 | 是本次请求的整体平均值，不是只计算逐 token 解码阶段的速度。 |
| `gpu_before` / `gpu_after` | 请求前后对指定物理显卡的两次 `nvidia-smi` 采样 | 是整卡占用，可能包括其他进程；不是本项目独占量，也不是运行期间的显存峰值。 |
| `finish_reason` | 模型服务说明为什么停止生成 | `stop` 不证明文字正确；`length` 等原因提示输出可能未完整结束。 |

当前使用非流式请求，应用收到完整响应后再展示文字，没有测量首 token 延迟；`ttft_client_seconds` 留空。两次显存采样之间发生过什么，不能靠两个数字还原。vLLM 也可能保留显存用于后续请求，因此一次解析结束后显存未明显下降，并不自动说明泄漏。

本平台同一时间运行一个任务，任务内按页依次请求。取消发生在页与页之间；已经发送的当前页请求不会因此立即停止。HTTP 超时也只说明应用没有按时拿到结果，不能据此断言模型端已经停止计算。

## CER 能回答什么，不能回答什么

CER 是字符错误率，本项目的计算方式为：

```text
CER = 将模型输出改成参考文本所需的最少字符编辑次数 ÷ 参考字符数
```

编辑包括插入、删除和替换。比较前先做 Unicode NFKC 归一化并删除空白；保留标点和 Markdown 符号。换行和空格差异因此不计入，但多出的 Markdown 标记仍可能增加分数。具体口径见[样本与评测说明](样本与评测说明.md)。

CER 越低，说明在这一口径下文字越接近参考；它可能大于 1，不能简单当成“准确率 = 1 − CER”。双栏文字顺序不同、标点差异、多输出解释，也会影响分数。即使 CER 为 0，也只能说明归一化文本一致，不能证明模型理解了业务。

表单样本的字段覆盖率只检查预期值是否出现，尚不验证键和值的对应关系。表格样本按 HTML `td` / `th` 中的文字匹配并保留重复次数，尚不验证行列位置及合并单元格。因此覆盖率很高时，仍要看原图核对结构。

本项目六页合成样本用于检查链路和练习评测方法，不代表真实客户材料的准确率，也不足以给模型做全面排名。

## 本轮提交什么，才方便判断你学到了什么

只提交这一份小实验记录，不用另做新功能：

- 两次运行的任务 ID、相同的输入页与参数，以及原始结果 JSON 或能看清关键字段的截图。
- 自己对照原图找到的一处差异；若没有发现差异，写明检查了哪些部分，不必硬造一个错误。
- 两次的结束原因、HTTP 耗时和 CER，并用自己的话解释每个数字测了什么。
- 用 4～6 句话描述“图片如何变成文字、如何被评分、如何保存”，再指出本次结果至少一个不能证明的结论。

如果失败，提交失败阶段、错误内容、任务参数和已尝试的一步排查即可。先保留证据，再定位问题。完成页面操作、完成这份记录、能够脱离提示独立复跑，是三种不同程度的证据；这份材料不预先判定你已经掌握。
