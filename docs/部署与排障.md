本页面向第一次在实验室共享服务器上部署模型的学习者。下面使用示例项目目录 `~/work/fde-doclens`，模型目录为 `~/work/models/HunyuanOCR-1.5`。除特别说明，命令都在已经 SSH 登录服务器的终端中执行。

**状态说明：截至 2026-11-16 本页更新，加入运行时 RoPE 覆盖和本项目 Python 头文件路径后，模型启动已通过，`/v1/models` 已列出 `tencent/HunyuanOCR`。历史验收完成6张样本、1页上传PDF和1次复跑，共8次真实页面请求，均正常结束。模型就绪不等于识别质量已通过；最终实测结果以项目 README 和 `evidence/` 中的实际记录为准。**

## 1. 先分清三个部分

```text
你的浏览器
    │ SSH 本地端口转发
    ▼
服务器上的网页与业务 API：127.0.0.1:18400
    │ HTTP：图片 data URI + 固定任务提示
    ▼
服务器上的模型 API：127.0.0.1:18401/v1
    │ vLLM 调度与模型计算
    ▼
物理 GPU 1：HunyuanOCR-1.5
```

网页能打开，只能说明应用服务可访问。模型 API 能列出模型，也还不能证明一张图片解析正确。完整验收至少包含：模型就绪、提交真实图片、取得完整输出、对照原图检查、保存结果。

本项目把两类 Python 依赖分开：`.venv-app` 运行 FastAPI、图片处理和评测；`.venv-model` 运行 vLLM、PyTorch 和模型。这样可以分别排查“网页请求出错”和“模型加载出错”。应用服务不需要在自己的环境里再安装一份 PyTorch。

| 对象 | 本项目的名称或位置 | 用途 |
| --- | --- | --- |
| 应用服务 | `fde-doc-app.service` | 网页、上传、任务管理、结果保存 |
| 模型服务 | `fde-doc-model.service` | HunyuanOCR 推理 |
| 应用启动脚本 | `scripts/start_app.sh` | 启动一个 Uvicorn worker，监听 18400 |
| 模型启动脚本 | `scripts/start_model.sh` | 限制 GPU、并发和上下文，监听 18401 |
| 模型名称 | `tencent/HunyuanOCR` | HTTP 请求中的 `model` 值 |
| 固定权重版本 | `47644ecc4fc854efa4f505155158831f36773ee4` | 确保这次复现使用同一版文件 |

服务名称中的 HunyuanOCR 与本地目录中的 HunyuanOCR-1.5 并不矛盾：前者是对外 API 名称，后者便于识别本地下载的模型版本。

## 2. 共享 GPU 的使用边界

启动前查看当前资源，不能沿用昨晚的截图：

```bash
cd ~/work/fde-doclens
nvidia-smi --query-gpu=index,name,memory.total,memory.used,memory.free,utilization.gpu --format=csv
free -h
df -h .
```

启动脚本默认使用物理 GPU 1，可通过 OCR_PHYSICAL_GPU 选择其他单张显卡，并检查所选显卡至少还有 **24 GiB 可用显存**。这个检查是启动门槛；它不表示本项目将占用 24 GiB。如果门槛未达到，脚本会主动退出，等待其他任务结束或重新协商资源即可。

`CUDA_VISIBLE_DEVICES=1` 让该进程只能看到物理 GPU 1。进程内部会把唯一可见的卡重新编号为 `cuda:0`。因此，“服务器 `nvidia-smi` 显示 GPU 1”与“模型内部显示 `cuda:0`”可以同时正确，不能仅凭 `cuda:0` 就认为占用了原有项目的物理 GPU 0。

当前启动设置为：

| 设置 | 当前值 | 为什么这样设置 |
| --- | --- | --- |
| `--gpu-memory-utilization` | 默认 `0.60` | 给其他工作留下预算空间 |
| `--max-model-len` | `8192` | 控制输入与生成的总上下文长度 |
| `--max-num-seqs` | `1` | 同时只处理一个模型序列 |
| 每次请求图片数量 | `1` | 每页依次推理，控制瞬时负载 |
| 应用任务并发 | `1` | 有任务执行时，新任务返回 409 |
| 单任务页数 | 最多 `6` | 便于观察、取消和复核 |

**60% 是 vLLM 的显存预算参数，不是 GPU 硬隔离，也不是保证任何时刻都不超出的系统配额。** 它不限制其他用户占用剩余显存，也不将计算单元固定分给本项目。即使显存仍有余量，运行推理时 GPU 利用率也可能接近 100%。启动前的可用空间还可能在检查后被别人的进程使用。

页面记录的 GPU 数据是整张物理卡的采样，包含其他进程；推理前后两次采样不是模型显存峰值。请把这些信息与 `nvidia-smi` 进程列表一起解释，不能将整卡显存增量直接写成“模型准确占用”。

## 3. 环境准备与安装顺序

已有环境无需为阅读文档重新安装。以下顺序用于首次部署或确实需要重建环境时；先结束本项目自己的服务，再处理对应环境，避免一边运行一边改依赖。

```bash
cd ~/work/fde-doclens
mkdir -p evidence logs
bash scripts/install_app_environment.sh
bash scripts/install_model_environment.sh
```

两个安装脚本均会运行 `pip check` 并保存依赖版本。模型环境固定使用 `vllm==0.18.1`；实际安装的 PyTorch、Transformers 等传递依赖应查看冻结文件，不能仅凭网上另一篇教程推断。

### 本轮遇到的问题一：系统 Python 3.12 没有 ensurepip

普通的 `python3 -m venv .venv-model` 可能提示 `ensurepip` 不可用。`venv` 创建 Python 环境，而 `ensurepip` 通常负责把 pip 放进新环境；部分服务器系统包没有包含后者。这不等于 Python 解释器损坏。

本项目的安装脚本已经采用下面的方式：

```bash
python3 -m venv --without-pip .venv-model
"${OCR_BOOTSTRAP_PYTHON:-python3}" -m pip --python "$PWD/.venv-model/bin/python" install --index-url https://pypi.tuna.tsinghua.edu.cn/simple pip 'vllm==0.18.1' 'pillow>=10.0.0'
```

第一步只建立环境，跳过 pip 初始化；第二步借用已有环境的 pip，明确把安装目标指向 `.venv-model/bin/python`。这里安装的目标是新环境，不修改引导 Python 的依赖。应用环境采用同样机制，目标为 `.venv-app`。

如果服务器上的引导 Python 路径不同，可设置脚本支持的 `OCR_BOOTSTRAP_PYTHON`，指向一个已有 pip 且支持 `--python` 参数的 Python。不要因为安装失败就运行 `sudo pip install`，也不要直接升级共享环境中的 PyTorch。

确认安装目标和依赖关系：

```bash
.venv-model/bin/python -m pip --version
.venv-model/bin/python -m pip check
.venv-app/bin/python -m pip --version
.venv-app/bin/python -m pip check
```

### 本轮遇到的问题二：Triton 编译提示找不到 Python.h

`Python.h` 是 Python 的 C 开发头文件。模型加载以后，Triton 或相关扩展仍可能临时编译小型本地代码；“PyTorch 能 import”并不能保证编译所需的头文件齐全。

本项目将头文件放在自己的 `.tools/python-dev/` 下，由 `scripts/start_model.sh` 设置：

```bash
export CPATH="$PWD/.tools/python-dev/usr/include/python3.12:$PWD/.tools/python-dev/usr/include${CPATH:+:$CPATH}"
```

历史验收使用了一份项目内的 Python 3.12 头文件副本。公开版不附带原主机路径；自行运行准备脚本后会生成本机的 evidence/python-headers.json。

换一台服务器重新准备时，可以使用：

```bash
python3 scripts/prepare_python_headers.py
test -f .tools/python-dev/usr/include/python3.12/Python.h
```

脚本在项目目录中执行 `apt-get download libpython3.12-dev`，再用 `dpkg-deb --extract` 解包；它不安装系统软件包，也不需要 sudo。该方法要求服务器的软件源中有匹配的 Python 3.12 开发包，且能运行 `apt-get`、`dpkg-deb`。若软件源没有这个包，先核对服务器系统和 Python 版本，不能随意下载其他 Python 版本的头文件混用。

也可以使用 `--copy-from`，传入已经解包的 `usr/include` 目录。这个目录下应包含 `python3.12/Python.h`；传入的是 include 目录，而不是 `Python.h` 文件本身。

## 4. 本轮模型启动兼容问题

### 4.1 日志开关需要使用当前版本接受的写法

vLLM 0.18.1 的启动脚本使用：

```bash
--no-enable-log-requests
```

如果报 `unrecognized arguments`，先确认实际启动的是 `.venv-model/bin/vllm`，并查看其帮助输出，不要把不同版本教程里的开关混在一起。当前脚本已使用上面的形式。该设置关闭逐请求日志开关，正常启动日志和错误信息仍会保存在本项目模型日志中。

### 4.2 `xdrope.py` 中出现 `assert positions.ndim == 2`

本轮真实错误发生在初始化的 `profile_run` 阶段。模型权重已经载入，随后位置编码层要求二维位置张量，却收到了普通一维位置张量。这一报错不是“显存不足”的同义词，反复增大显存预算不能修正配置字段不一致。

只读排查确认了下面的调用关系：

1. 固定版本权重的 `config.json` 将 XD-RoPE 参数放在 `text_config.rope_parameters` 中，四个分段为 `[16, 16, 16, 16]`。
2. vLLM 0.18.1 的 `uses_xdrope_dim` 检测逻辑读取 `xdrope_section` 或 `rope_scaling.xdrope_section`，未从该新字段取得分段，因此得到维度数 `0`。
3. runner 据此创建一维位置输入；实际位置编码层却按 `rope_parameters` 建立了 XD-RoPE，于是触发二维断言。
4. 图像请求的 Hunyuan 位置构造代码还会读取 `hf_config.rope_scaling`，因此只补一个顶层 `xdrope_section` 不够。

修复已放入 `scripts/model_overrides.py`：读取本地配置，将原 `rope_parameters` 原值复制到运行时覆盖的 `text_config.rope_scaling`，然后由启动脚本通过 `--hf-overrides` 传给 vLLM。它会检查模型类型和分段值，遇到意外配置或已有冲突字段时拒绝继续，避免静默更改未知模型。

这项适配**不修改原 `config.json`，也不修改权重文件**。每次启动使用的覆盖内容保存为 `evidence/model-runtime-overrides.json`。只读 CPU 配置测试中，检测结果由 `0` 变为 `4`，原 `rope_parameters` 保持不变。随后在同时补齐 Python 头文件路径后，真实模型已启动并通过 `/v1/models` 就绪检查；单页及多页解析质量仍需独立验收。

可以单独检查覆盖内容，而不启动模型：

```bash
python3 scripts/model_overrides.py ~/work/models/HunyuanOCR-1.5
```

官方归档说明将 vLLM 0.18.1 列为可用部署方案，但当前固定权重的配置字段与运行时检测路径仍需要本项目这项兼容适配。参考：[腾讯 vLLM 部署说明](https://github.com/Tencent-Hunyuan/HunyuanOCR/blob/main/docs/inference/archive/vLLM.md)、[vLLM 0.18.1 配置解析代码](https://github.com/vllm-project/vllm/blob/v0.18.1/vllm/transformers_utils/config.py)。

## 5. 启动、检查与停止自己的服务

服务安装器只创建本项目的两个用户级 unit，不执行开机自启：

```bash
cd ~/work/fde-doclens
python3 scripts/install_user_services.py
systemctl --user start fde-doc-app.service
systemctl --user start fde-doc-model.service
```

这里的 `start` 只说明 systemd 接受了启动请求。模型还需要加载、显存预检查、编译或预热，不能在命令返回后马上宣布“部署成功”。

```bash
systemctl --user status fde-doc-app.service fde-doc-model.service --no-pager
tail -n 100 logs/model.log
curl -fsS http://127.0.0.1:18401/v1/models
curl -fsS http://127.0.0.1:18400/api/status
```

排查时按顺序看：服务是否仍在运行、模型日志的最后一个错误、18401 能否返回所需模型、应用状态中的 `model_ready` 是否为 `true`。模型没有就绪时，应用仍可提供样本浏览和历史结果，但不会伪造 OCR 输出。

停止本次实验：

```bash
systemctl --user stop fde-doc-app.service
systemctl --user stop fde-doc-model.service
systemctl --user status fde-doc-app.service fde-doc-model.service --no-pager
nvidia-smi
```

这些命令只针对自己的两个用户服务。不要使用 `pkill -f python`、`killall vllm` 或按名称批量杀进程；共享服务器上其他实验可能使用相同的程序名。查看 GPU 进程时也不能把其他人的 PID 当成本项目残留。

### 模型运行八小时后停止，是预设的上限

`fde-doc-model.service` 设置了 `RuntimeMaxSec=28800`，即单次运行最多八小时；`Restart=no` 表示停止后不会自动反复拉起。应用服务没有这项八小时上限，因此网页可能仍能打开，但显示模型未就绪。

达到上限后，systemd 可能报告 timeout 或 failed 状态。这是运行时限触发的退出，不能仅凭 failed 就断定模型崩溃。查看时间和服务结果：

```bash
systemctl --user show fde-doc-model.service -p ActiveState -p SubState -p Result -p ExecMainCode -p ExecMainStatus -p ActiveEnterTimestamp -p RuntimeMaxUSec
journalctl --user -u fde-doc-model.service -n 60 --no-pager
```

若记录显示服务已达到运行上限，下一次学习前重新检查共享资源，再执行 `systemctl --user start fde-doc-model.service`。八小时上限不是定时任务，也不保证 SSH 退出、服务器重启后服务一定继续运行；用户级服务的生命周期仍取决于服务器配置。

## 6. 在自己电脑上打开网页

两个服务都只监听服务器自己的 `127.0.0.1`。因此在个人电脑浏览器输入 `http://127.0.0.1:18400` 前，需要先建立 SSH 转发。在个人电脑的新终端中执行：

```bash
ssh -N -L 18400:127.0.0.1:18400 YOUR_USER@YOUR_SERVER
```

保持该终端运行，再在个人电脑浏览器打开 `http://127.0.0.1:18400`。这里左边的 18400 是个人电脑端口，右边的 18400 是服务器应用端口。页面由应用转发请求给模型，不需要另外把 18401 暴露到公网。

如果个人电脑端口已经占用，可把命令左侧改为 `18410:127.0.0.1:18400`，对应浏览器使用 `http://127.0.0.1:18410`。如果网页完全打不开，先查 SSH 转发与应用服务；如果网页能打开但显示模型未就绪，则查模型服务和 18401。

## 7. 如何区分“请求完成”和“解析质量好”

| 观察到的结果 | 能说明什么 | 还不能说明什么 |
| --- | --- | --- |
| `/v1/models` 返回 200 | 模型端点可访问、能列出模型 | 当前文档能够完整解析 |
| `POST /api/jobs` 返回 202 | 应用接受了后台任务 | 推理已经完成或答案正确 |
| 页面 `status=completed`、`finish_reason=stop` | 返回非空输出且正常结束 | 没有漏字、错字、错表格 |
| `finish_reason=length`、页面为 `partial` | 已有部分输出，但触及生成限制 | 可当作完整解析结果使用 |
| CER 较低 | 与对应全文参考的字符差异较小 | 表格结构、布局或语义完全正确 |
| 字段或单元格覆盖较高 | 预期值在输出中出现较多 | 字段关联、行列关系正确 |

文字样本评测使用 `structured_parse`，提示为“提取图中的文字。”。这是因为合成参考包含全部可见文字，而 `doc_parse` 的官方提示明确忽略页眉页脚；使用后者对全文参考计算 CER，会把任务要求造成的差异误算成识别错误。本项目遇到这类不一致会说明原因并留空 CER。

CER 是归一化后的编辑距离除以参考字符数，越低越好，可能大于 1。归一化会统一 NFKC 字符并删除空白，但保留标点及 Markdown 符号。它不是“正确率百分比”。表格覆盖按 HTML `td/th` 内容计数，尚未检查单元格位置；字段覆盖也不判断字段和值的对应关系。

本项目记录的是非流式 HTTP 请求耗时。用输出 token 数除以这段耗时得到平均速率，不能将其叫作纯解码吞吐；其中还包含图像处理、输入计算、排队和传输。结果中的首 token 时间为 `null`，不能从总耗时猜一个 TTFT。

首次真实验证建议只提交一张自带中文样本，确认输出与原图相符后，再运行多页、表格和 PDF 验证。`scripts/run_acceptance.py` 会进行有边界的真实模型验收，包含六张合成样本及一张 PDF 转换页；它会实际占用 GPU，不是只检查代码的单元测试。确认资源空闲且模型就绪后再运行：

```bash
.venv-app/bin/python scripts/run_acceptance.py
```

验收脚本的输出不会把合成样本成绩包装成真实业务文档准确率。上传的新文档通常没有参考答案，应人工对照原图，不应自动展示一个凭空生成的准确率。

## 8. 日志、版本与复现证据在哪里

以下路径相对于 `~/work/fde-doclens`。有些文件由安装、启动或验收脚本运行后才会出现；缺少文件意味着尚未产生该项记录，不能补写一个假结果。

排障时先记录“在什么时间、执行什么命令、最后一段报错是什么”，再做一处改变并重复同一个最小验证。不要同时升级 vLLM、修改显存比例和替换权重，否则很难知道是哪一步解决了问题。

## 9. 常见现象的下一步

| 现象 | 先检查 | 推荐处理 |
| --- | --- | --- |
| `ensurepip is not available` | 是否绕过了项目安装脚本 | 使用 `--without-pip` 与 bootstrap pip 的既定流程 |
| `Python.h: No such file or directory` | 头文件是否存在、启动是否经过 `start_model.sh` | 准备本项目头文件并检查 CPATH |
| `positions.ndim == 2` 断言 | 覆盖生成脚本及当前模型版本 | 使用本项目运行时适配，保留原始权重 |
| 模型服务刚启动就退出 | `logs/model.log` 最后一段、当前 GPU 1 空闲显存 | 先区分资源门槛、参数错误、编译错误，再处理对应原因 |
| 八小时左右服务停止 | systemd 结果与运行时长 | 确认上限触发后，重新检查资源再启动 |
| 提交任务得到 409 | 当前 `active_job` | 等待现有任务结束，或在页面请求取消 |
| 提交任务得到 503 | `model_ready` 与模型服务日志 | 修复模型服务后重试；不会自动返回演示答案 |
| 点击取消后当前页仍在执行 | 取消标记及上游请求耗时 | 取消在页与页之间生效；当前页完成或超时后停止后续页 |
| 输出看起来只完成一半 | `finish_reason`、页面状态、输出 token 数 | 标记部分结果；在上限内调整生成长度或选择更简单页面 |
| 上传失败 | 文件真实格式、大小和 PDF 页数 | 使用 PNG/JPEG/WEBP/PDF，文件不超过 12 MiB，PDF 不超过六页 |

学会解释这些现象，比记住一条启动命令更有价值。代码通过测试属于实现证据；能自己定位一次失败、说明指标的边界，并用原图验收输出，才是学习掌握证据。
