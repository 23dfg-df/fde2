# 从 DocLens 接续开源项目：交付、推理性能与 Agent

检索日期：**2026-11-16**。本文是基于官方仓库、固定版本文档和招聘页面整理的学习规划，**不代表已经完成这些项目的部署、复现或性能测试**。后续开始操作时，应再次检查版本、依赖和可用资源。

推荐主线是：**DocLens 导出 Markdown → WeKnora 知识库交付 → vLLM 推理性能实验 → tRPC-Agent-Go 工具工作流**。每轮只完成一个能单独验收的小任务；本文列出后续方向，不要求一次做完。

## 1. 为什么选择这条路线

DocLens 已经覆盖文档入口：图片或 PDF 经过模型解析，产生文字、Markdown 或表格，并保留耗时和规则评测。接下来值得练习的是：怎样把输出接入另一个系统、判断回答是否有依据、测量服务性能、解释故障，并交付别人可以重新运行的结果。

| 阶段 | 项目与固定研究版本 | 本阶段解决的问题 | 可交付的证据 |
|---|---|---|---|
| 第一阶段 | [Tencent/WeKnora v0.9.0](https://github.com/Tencent/WeKnora/releases/tag/v0.9.0) | 把解析结果接入知识库，并验证检索与引用 | 一页文档、索引状态、问答原始结果、引用、复现记录 |
| 第二阶段 | [vLLM](https://github.com/vllm-project/vllm)，实验时固定已验证的版本 | 相同模型面对不同请求负载时，延迟、吞吐和显存如何变化 | 固定输入、启动配置、两组原始测量、指标计算和解释 |
| 第三阶段 | [tRPC-Agent-Go v1.12.0](https://github.com/trpc-group/trpc-agent-go/releases/tag/v1.12.0) | 用工具调用组织文档处理与知识查询，并处理超时和取消 | 工具定义、工作流、成功与失败用例、可追踪的请求记录 |

WeKnora 与已有知识库助手存在功能重叠。新阶段的价值应体现在接通真实数据、对照评测和交付记录上。只完成安装、换一张界面截图，不能证明自己理解系统；显存占满也不能说明实验设计充分。

## 2. 第一阶段：WeKnora 的一页最小复现

### 2.1 已核实的能力与边界

研究版本 v0.9.0 提供 Lite 模式，使用 SQLite 与内存队列，减少外部数据库和消息队列依赖。官方标准安装建议从 4 核 CPU、8 GB 内存开始，**不包含模型权重占用**；这不是对所有 Lite 工作负载的实测保证。[Lite 说明](https://github.com/Tencent/WeKnora/blob/v0.9.0/docs/LITE.md) · [安装说明](https://github.com/Tencent/WeKnora/blob/v0.9.0/website-docs/01-getting-started/02-installation.md)

WeKnora 原生支持 `.md`、`.markdown`，Markdown 可以由 Go 内置解析器读取，不需要为这一步再启动 Python 文档解析服务。其知识 API 也提供文件上传和手动文本创建入口。[解析实现](https://github.com/Tencent/WeKnora/blob/v0.9.0/internal/infrastructure/docparser/builtin_converter.go) · [知识 API](https://github.com/Tencent/WeKnora/blob/v0.9.0/website-docs/04-api/02-api-knowledge.md)

本轮研究发现 Lite 说明与安装文档对免注册、免登录范围的描述存在差异。因此本文不承诺 Lite 已验证完全免登录，实际部署时应确认行为。

### 2.2 先分清两种模型接口

| 接口 | 输入与输出 | 在知识库中的职责 |
|---|---|---|
| Chat / 生成接口 | 输入消息，输出自然语言回答 | 根据问题和检索片段组织回答 |
| Embedding / 向量接口 | 输入一段或一批文本，输出固定维度的数值向量 | 为文档建立向量索引，并把问题编码为可检索的向量 |

常见 OpenAI 兼容路径分别为 `/v1/chat/completions` 和 `/v1/embeddings`。路径相似不表示能力相同：一个只部署生成模型的 vLLM 服务，不会因此自动具备可用的向量接口。WeKnora 的自定义厂商可以对接兼容协议，但聊天模型与向量模型需要分别配置。[模型配置说明](https://github.com/Tencent/WeKnora/blob/v0.9.0/website-docs/03-features/06-models.md)

原有应用内部能调用 BGE，也不等于已经存在一个可供另一个系统访问的 embedding HTTP 服务。接入前应验证批输入、向量维度、超时、查询与文档的编码规则，并保持索引与查询使用兼容的模型配置。第一轮可优先评估 CPU embedding，减少新增 GPU 权重。

### 2.3 这一轮只做一个任务

> 固定 WeKnora v0.9.0，用一份已完成 OCR 的 `LAB-NOTICE-001` Markdown 建库，确认索引完成，并回答一个能定位到这份文档的问题。

建议按以下顺序进行，每个检查点失败后先排查当前问题：

1. 从 DocLens 导出该页 Markdown，人工查看正文，确认文件确实来自选定任务。
2. 确认聊天与向量接口分别可用，在 Lite 中选择对应模型配置。
3. 手动上传这一份 Markdown，记录文档 ID，等待索引完成。
4. 提出一个答案能在文档中找到的问题，保存原始响应及引用截图。
5. 对照原文检查答案和引用是否一致，记录不确定项。

**验收条件：**文档成功进入索引；一次问答得到可核对的答案与来源；重做步骤所需的版本和配置已记录。问题应由学习者先从样本中选定，避免把模型生成的答案直接当参考答案。

本轮只做人工导出和上传。自动化串联是后续独立任务，需要编写“读取 DocLens 完成任务 → 获取 Markdown → 调用 WeKnora 知识 API → 保存两边文档 ID”的适配代码。目前不把这条链路标记为已实现。

Markdown 导入成功也不意味着原 PDF 页码、版面坐标、图片资源和 OCR 任务来源自动完整保留。首轮引用能够证明什么，应按实际响应核验。

### 2.4 分别记录两类证据

| 实现证据：系统确实做到了什么 | 学习掌握证据：学习者能独立说明什么 |
|---|---|
| 输入 Markdown、文件摘要、模型配置快照 | 能指出该文件对应哪次 OCR 输出 |
| 上传返回的文档 ID、索引完成状态 | 能解释“上传成功”和“可以检索”为什么是两个状态 |
| 问答原始 JSON、引用截图、人工核对结论 | 能解释 OCR 完成后为什么还需要 embedding |
| 实际版本、启动方式、遇到的问题 | 能沿着一个问题说明检索片段和最终回答的关系 |

配置快照不包含 API 密钥、私人地址或账户信息。助手运行成功属于实现证据；学习者尚未解释或独立操作的项目，学习掌握状态应写“待验证”。若记录到 `PROGRESS.md`，也应保留这一区分。

### 2.5 最小任务通过后再扩展

后续每轮只选一项：整理 20–30 条有出处的问题；比较同模型、同文档下两套知识库的检索和引用；注入一个超时或空 OCR 结果；实现自动导入适配。比较时保留失败样本，不能只展示最成功的一问。

WeKnora v0.9.0 的内置评测有 API 入口，结果存储在内存中，重启会丢失；并发默认值与 CPU 数量相关。在共享机器上，应显式限制评测并发并导出结果，不直接使用高核数机器推导出的默认并发。[官方评测说明](https://github.com/Tencent/WeKnora/blob/v0.9.0/website-docs/03-features/15-evaluation.md)

## 3. 第二阶段：vLLM 推理性能工程

vLLM 是推理服务框架，提供连续批处理、KV cache 管理与 OpenAI 兼容服务。这里的目标是解释服务行为，并在相同条件下测量一次配置变化带来的影响。[官方仓库](https://github.com/vllm-project/vllm)

首个独立任务建议为：**同一个小文本模型，完成并发 1 与并发 2 的有界对照实验。**

- 固定模型提交、服务版本和提示词；使用 20 条输入、相同的最大输出长度，例如 128 tokens。
- 预热与正式测量分开；明确请求数、并发和请求速率，避免测试工具的默认无限速率压满服务。
- 保存每次请求是否成功、实际输入输出 token、完整响应耗时，以及采样时刻与显存值。
- 分别计算端到端延迟 p50/p95、总输出吞吐和成功率；输出总 token 除以该轮测试墙钟时间，才是这里的总体输出吞吐。
- 解释吞吐提高是否伴随单请求等待变长，并保留异常请求。20 条输入只适合入门比较，不能据此声称生产容量上限。

`max_model_len`、`max_num_seqs` 以及 CUDA graphs 等配置都会影响显存。控制变量时一次只改变一个参数，不把不同模型、不同输出长度的结果混成一个排行榜。[官方内存说明](https://github.com/vllm-project/vllm/blob/main/docs/configuration/conserving_memory.md)

工具参数应按实际安装版本核对。[官方基准工具文档](https://docs.vllm.ai/en/latest/cli/bench/serve.html)介绍并发、请求速率与预热控制。首 token 延迟 TTFT 需要相应的流式测量；当前非流式请求等待完整响应的时间，不能写成 TTFT。

交付物为配置、固定输入、两组原始结果、指标计算及一页中文解释。性能结论必须来自本轮真实测量，不填入预期成绩，也不把整卡采样最大值称为模型进程的瞬时显存峰值。

## 4. 第三阶段：tRPC-Agent-Go 工具工作流

研究版本为 v1.12.0，Go 模块声明要求 Go 1.21。它适合在已经能读懂 Python API、任务状态与超时处理之后再学，届时先补最少的 Go 基础。[官方仓库](https://github.com/trpc-group/trpc-agent-go) · [固定版本 go.mod](https://github.com/trpc-group/trpc-agent-go/blob/v1.12.0/go.mod)

最小业务可以是“文档处理工单助手”：提供查询 OCR 任务与检索知识库两个工具，先完成一个只读工作流，再分别验证成功、超时和取消路径。应保存请求关联信息，能够查清哪个步骤调用了哪个服务。

框架进程主要使用 CPU；复用现有模型端点不需要再加载一份 GPU 权重，但调用仍然会消耗上游推理资源。模型支持普通聊天接口，也不代表它的工具调用格式和行为已通过验证；应先做一个明确的工具调用契约检查，再接复杂工作流。

这一阶段不是把整个业务改写成 Go。保留原有 API、业务和数据访问分层，让工作流通过已有接口调用它们即可。

## 5. 共享 GPU：预算先于负载

以下是建议的初始实验预算，**不是上游官方显存最低要求，也不是已经测得的资源占用**。

| 阶段 | 初始安排 | 开始前必须核实 |
|---|---|---|
| WeKnora 一页导入 | 应用侧可先计划 4 核 CPU、8 GB 内存；优先 CPU embedding；聊天复用已有端点；一次只处理一个任务 | 现有端点是否可用、CPU embedding 是否能接入、共享服务是否正承担其他请求 |
| vLLM 有界测试 | 只使用一张 GPU；若需要另起小文本模型，先以 8–12 GiB 为目标估算并实测；输出和并发均受限 | 权重、缓存、上下文及运行时空间是否足够；能否保留约定给其他任务的余量 |
| tRPC 工具工作流 | CPU 运行框架，复用已有服务；最初只启动一个工作流 | 请求速率、超时、取消和上游容量是否明确 |

8–12 GiB 可能不适合具体模型或启动配置。若预算内无法启动，应缩小模型、上下文或并发，或调整预约时间；不能为了达成“用了 GPU”而自动扩大占用。初次做性能基线时，不同时运行 OCR 批处理、知识库评测和新模型压测，否则难以解释资源竞争。

每次实验前重新查看 GPU、CPU、内存和磁盘状态；空闲显存只描述当时的快照，不代表已经预约到资源。vLLM 显存比例参数不是硬件资源隔离。结束后检查本次启动的进程与资源释放情况，不停止其他人的任务。
